# Initial Threat Model

Status: Local development security baseline is implemented. Targeted PostgreSQL tests cover auth/session lifecycle, public-account gating, recovery and verification tokens, request validation, owner isolation, schema, proxy-header trust, secret-safe logging and Group-admin privilege boundaries. Group administration is break-glass-only per [ADR-0023](../decisions/ADR-0023-break-glass-group-administration.md). Public-account code remains disabled by default; no external SMTP, hosted worker, edge control or production environment has been tested. This is not production approval.

Assets: customer identities/addresses, session secrets, order history, stock accuracy, administrative privileges and developer credentials.

Trust boundaries: browser→HTTP API; Stripe-hosted Checkout→Stripe; Stripe-signed webhook→payment API; browser→admin; public ingress/reverse proxy→application; application→PostgreSQL; application→SMTP through the account outbox; configuration→runtime; generated API types→frontend. Browser payloads, provider event bodies until signature verification, forwarded headers, SMTP responses and administrative form input are untrusted until validated. Module ownership is a code boundary, not separate database credentials.

| Threat | Impact | Current control | Verification and residual risk |
|---|---|---|---|
| Cross-customer object access | Address/order disclosure | Owner-scoped selectors on lists, detail, mutations and replay | PostgreSQL API test confirms another user's UUID cannot list/read/act on order |
| Price/status/role tampering | Fraud or privilege escalation | Explicit input allowlist; server totals; staff fields read-only | Submit forged totals, roles and nested fields |
| CSRF including anonymous login | Unwanted actions or login confusion | Explicit Django CSRF checks on unsafe auth/order routes; JSON token bootstrap | Missing/invalid token and untrusted Origin tested across customer registration, login, logout, order creation, payment and cancellation; trusted local Vite Origin has a positive test |
| Session theft/fixation | Account compromise | HttpOnly/Secure/Lax, login rotation, bounded expiry, logout revocation; password reset changes the auth hash and invalidates prior sessions | Session rotation, expiry, logout and recovery-driven session invalidation tested |
| Password guessing/enumeration | Account takeover | Generic login failures and atomic PostgreSQL source plus source+identity limits for customer/Admin login; local registration and password reset have separate policies; password-reset response is account-independent | PostgreSQL threshold, normalization, source isolation, concurrency, generic recovery response, one-use reset, password validators, session invalidation, HMAC storage, CSRF ordering and fail-closed behavior tested; distributed attacks remain possible |
| Distributed guessing or account-flow abuse | Account takeover, mailbox flooding or resource exhaustion | HMAC-pseudonymous source, source+identity and global-identity counters; generic public account responses; fail-closed on PostgreSQL throttle failure | Cross-source identity behavior is tested; quotas remain application/DB-level and do not replace edge controls, CAPTCHA/bot mitigation or monitoring |
| Recovery/verification token theft or replay | Account takeover or false account state | Django password-reset tokens, one-hour expiry, one-use password-state binding, signed one-hour verification token, POST-only confirmation and URL-fragment handling | PostgreSQL tests cover success/replay/invalid-token/session behavior; local verification is informational only and a console reader can see demo links |
| Proxy header spoofing or misconfiguration | Throttle bypass, incorrect secure-request detection or host/protocol confusion | Remove forwarded headers from untrusted peers; accept them only from configured direct-peer CIDRs; do not trust forwarded host/port | Forged/untrusted, trusted-chain and malformed-header tests pass; production proxy topology and CIDRs are not provisioned or verified |
| SMTP outage, ambiguous delivery or outbox abuse | Lost/delayed or duplicate verification/reset messages; storage growth | Transactional minimal outbox, one-row just-in-time claims, row locks, capped retries and dead-letter state; generate tokens at delivery time | PostgreSQL retry/dead-letter and concurrent slow-delivery tests pass; SMTP is locmem-tested only, delivery is at-least-once for the current in-flight message, and scheduled operation, alerting and retention are not configured |
| Forged/replayed payment webhook | Unauthorized capture, duplicate order confirmation or stock consumption | Verify Stripe signature against exact raw request bytes; unique event IDs; conflicting replay payloads rejected; only the allowlisted authorization event is processed | Invalid signature, duplicate ID, distinct repeated authorization, mismatched amount, late authorization and provider retry tests pass; real Stripe sandbox delivery is not validated |
| Checkout tampering or unauthorized capture | Overcharge, payment for another order or capture after stock reservation ended | Build hosted session from immutable database snapshots; exact amount/currency/order/attempt/intent/deadline/reservation validation; manual capture only after durable state claim; browser return never confirms | PostgreSQL state and stock tests plus adapter contract tests pass; sandbox credentials are unavailable for a provider-hosted end-to-end exercise |
| Ambiguous/failed provider capture or delayed webhook | Order stays pending while a temporary card authorization may remain visible | Persist minimal retryable provider receipt, use stable capture/cancel idempotency keys, do not confirm before provider success | Simulated transient capture failure resumes safely on redelivery; no hosted alert/reconciliation worker or provider retry exhaustion handling is deployed |
| Malicious hosted checkout URL or payment-secret disclosure | Phishing redirect or provider account compromise | Accept only HTTPS URLs on exact `checkout.stripe.com` host; test-only secret prefixes; secrets stay server-side and provider error details are not returned | Adapter/config tests pass; provider dashboard access control and secret rotation are external operational gates |
| Concurrent checkout/replay | Oversell or duplicate charge effects | Row locks, constraints, scoped idempotency | PostgreSQL domain races/replay and API owner isolation/replay tests pass |
| Admin bypasses domain logic or group privilege escalation | Inventory/order corruption or unauthorized staff privilege | Catalog operations use owner services; stock counters are read-only and adjustment writes are permission-gated, locked and audited; Group admin is restricted to active staff superusers | PostgreSQL tests verify ordinary staff cannot grant their group `inventory.adjust_stock`, while the break-glass superuser can; broader order admin paths remain unimplemented |
| Stored description script | Browser compromise | Plain text, React escaping, no arbitrary HTML | Script-shaped strings render as text |
| Secret/PII in logs | Data leak | Allowlisted metadata; no bodies/cookies/passwords/addresses | Capture logs during errors and auth flows |
| Maintenance crash or parallel worker | Stock held too long, lost/duplicate notification intent | Deadline checks, durable intents, bounded `skip_locked` claims, persisted failures and retry on a later pass | PostgreSQL tests cover failure/restart and concurrent claim; console output remains at-least-once in a crash-after-output window |
| Backup disclosure or restore overwrite | Account/order data exposure or data loss | Local backup is DEBUG-only; remote backup is explicit opt-in, requires versioned storage, HTTPS outside DEBUG, SSE-S3 and exact-version checksum verification; restrictive temporary-file modes; archive validation; source/existing-target refusal; fresh target and transactional restore | Moto S3 API plus disposable PostgreSQL round trip preserve representative data; no hosted bucket/IAM/lifecycle/restore drill. Dumps are plaintext on local temporary storage before upload and during restore; host compromise, disk exhaustion, broad credentials, or incorrect lifecycle remain risks. |
| Development stack exposed beyond host | Debug information or local account compromise | DEBUG Compose only, frontend and database ports bound to loopback, API private to Compose network, non-root app users, no image-baked credentials | Fresh Compose health/API/browser checks pass; a user-controlled tunnel/proxy or host compromise remains outside the boundary |
| Untrusted pull request influences CI or publishes an artifact | Repository token misuse or distribution of unreviewed images | GitHub Actions uses `pull_request`, global `contents: read`, no secrets/registry credentials, disabled checkout credential persistence, full-SHA-pinned actions, and uploads images only from pushes to `main` | The workflow does not prove a main push was reviewed. Until owners enable branch protection, required checks and reviews, main artifacts must not be promoted; hosted permissions and first run remain unverified |
| Scanner reports expose matched secret material | Credential disclosure in CI logs or artifacts | Trivy JSON is written only to runner temporary storage; a tested policy parser prints severity, finding identifier, and location without the match; scan reports are not uploaded | Redaction policy unit tests pass; hosted runner behavior and scanner action execution remain unverified |
| Destructive migration | Lost history or stock | Expand/contract, review, local backup/restore commands before destructive local experiments | Clean/upgrade and disposable restore checks; backup tools remain local-only and do not protect hosted/real data |

Residual limitations and launch gates: `BLAST_ECOM_PUBLIC_ACCOUNT_FLOWS_ENABLED` is off by default, and passing tests do not demonstrate real SMTP delivery or safe deployment. App/database rate controls do not provide edge-level or volumetric protection. Proxy CIDRs must match a reviewed topology and the ingress must sanitize/append client headers correctly. The outbox needs supervised scheduling, alerting and a retention policy. Staff MFA, account lifecycle/privacy processes, hosted TLS/secrets and external provider threats have not been implemented or assessed. Remote backup code exists, but hosted bucket access policy, lifecycle enforcement, scheduling, monitoring, key/identity restrictions and a real hosted restore have not been configured; retention tags alone do not enforce deletion. This document is a scoped engineering model, not production approval.
